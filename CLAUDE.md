# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

# Sculptor

Веб-справочник радиоэлектронных компонентов OpenYard, составы плат (BOM)
и серверов. Django 6.1 + PostgreSQL 18, интерфейс и документация на
русском.

Подробности — в `docs/` (оглавление в `README.md`). Перед изменением
раздела прочитай его документ: там записано не только «как», но и
«почему так», и многие решения выглядят странно, пока не знаешь причину.

## Устройство

| Приложение | Что внутри | Документ |
|---|---|---|
| `users` | своя модель пользователя, роли-группы и проверки прав (`roles.py`), профиль, роли сотрудников, журнал доступа (`access.py`), `init_roles` | `docs/users.md`, `docs/schema-history.md` |
| `components` | 27 таблиц компонентов, карточки, журнал изменений, картинки посадочных мест, фоновый рендер STEP | `docs/components.md` |
| `boards` | платы, ревизии, составы (BOM), импорт BOM из Excel | `docs/boards.md` |
| `servers` | серверы и их состав: позиции, строки, разузлование | `docs/servers.md` |

Карта модулей — `docs/architecture.md`. История изменений схемы базы и
порядок переездов — `docs/schema-history.md`.

**База, две схемы.** `sculptor` — таблицы Django. `public` — 27 таблиц
компонентов и представление `Parts`: их ведёт не Django (`managed = False`),
и в них же пишут другие программы. Поэтому:

- таблицы компонентов не меняются миграциями — ни колонки, ни индексы;
- ссылка на компонент — пара «таблица + ключ», внешних ключей на них нет
  (`components/refs.py`);
- данные о компоненте, которых нет в его таблице, живут в своих таблицах
  Django с префиксом `oy_` (журнал, картинки, заявки на рендер).

## Команды

Локально (Windows, venv в корне проекта):

```
venv\Scripts\python.exe manage.py runserver 8000
venv\Scripts\python.exe manage.py test
venv\Scripts\python.exe manage.py check
venv\Scripts\python.exe manage.py makemigrations --check --dry-run
```

Один тест или класс — через точку, с модулем темы:
`manage.py test components.tests.test_admin.ИмяКласса.test_метод`
(у `boards` и `servers` тесты одним файлом: `boards.tests.ИмяКласса`).

Линтер — `ruff` (настройки в `pyproject.toml`, ставится из
`requirements-dev.txt`, на сервер не идёт):
`venv\Scripts\python.exe -m ruff check .`, `ruff format --check .`.

`.env` в корне читает сам `config/settings.py` — переменные окружения
задавать отдельно не нужно. Пример — `.env.example`.

На сервере всё идёт через Docker Compose:

```
docker compose exec web python manage.py <команда>
docker compose logs -f web
docker compose up -d --build        # после обновления кода
```

Полезные команды проекта:

- `check_schema` — видит ли Django таблицы компонентов и в какой схеме;
- `check_step_render --render` — работает ли рендер STEP (рисует пробную
  картинку, а не только проверяет импорт пакетов);
- `render_step_images --dir model` — картинки посадочных мест пачкой из
  папки со STEP-моделями (`--dry-run`, `--replace`);
- `render_job <номер>` — повторить заявку на рендер руками;
- `relink_boards` — пересвязать строки BOM с библиотекой.

## Тесты

Тесты — пакет `components/tests/` (модуль на тему: `test_site`,
`test_library`, `test_forms`, `test_editing`, `test_duplicates`, `test_links`,
`test_history`, `test_step`, `test_admin`), `boards/tests.py`,
`servers/tests.py`, `users/tests.py`. Почти все —
`SimpleTestCase`, без базы: проверяется логика, а не данные. Новое поведение
сопровождается тестом того же вида. Если что-то нельзя проверить без базы —
выдели чистую функцию и проверяй её (так сделаны `_split_fields`,
`image_changes`, `upload_path`).

Перед тем как сказать «готово»: `manage.py test` и `manage.py check` должны
проходить. Если менялись модели — ещё `makemigrations --check`.

## Правила, на которых уже спотыкались

**Шаблоны.**
- Многострочные комментарии — только `{% comment %}…{% endcomment %}`.
  `{# … #}` работает в пределах одной строки; многострочный Django выводит
  на страницу обычным текстом.
- Текст на страницах пишется для пользователя. Объяснения «почему так
  сделано» — в комментарии шаблона или в документацию, не в интерфейс.

**HTMX.**
- Атрибуты `hx-*` — только поверх рабочих ссылок и форм и только при
  `htmx_enabled`: без файла htmx сайт работает обычными переходами.
- Фрагмент — частичный шаблон `{% partialdef имя inline %}` в том же файле,
  вид отдаёт `"шаблон.html#имя"`, если `request.htmx`.
- Скрипт, который оформляет элементы, регистрирует функцию в `window.OY`
  и вызывается из `htmx-setup.js` для каждого вставленного куска.
- Подробности — `docs/architecture.md`, раздел «Интерактивность: HTMX».

**Стили.**
- Цвета, отступы, скругления и шрифты — только токены из
  `components/static/components/tokens.css`. Их читают и сайт (`app.css`),
  и админка (`admin.css`); чисел цветов в стилях быть не должно.
- Тема выбирается атрибутом `data-theme` на `<html>`
  (`templates/_theme_boot.html`), одна на сайт и админку.
- В `admin.css` переменные Django объявлены через
  `:root, html[data-theme="light"], html[data-theme="dark"]`. Один `:root`
  проигрывает Django по весу селектора — не упрощать.
- Элементы админки, которые Django описывает через `id` (`#changelist`,
  `#toolbar`), перебиваются только такими же селекторами.

**Пользователи.**
- Модель пользователя — `users.User`. Ссылаться на неё только через
  `settings.AUTH_USER_MODEL` во внешних ключах и `get_user_model()` в коде.
- В журнале автор хранится логином строкой, не ссылкой — не менять.
- Права решает членство в группах (`users/roles.py`), а не механизм
  разрешений Django: таблицы компонентов неуправляемые.

**Django и данные.**
- Django 6.1: `ImageField.get_internal_type()` отвечает `"FileField"`.
  Проверять тип поля — через `isinstance`.
- `.values_list(...).distinct()` у модели с `Meta.ordering` возвращает
  повторы: поля сортировки попадают в запрос. Перед `distinct` — пустой
  `.order_by()`.
- Файлы картинок пишутся под точным именем: штатный `ImageField.save`
  при совпадении дописывает случайный суффикс. См.
  `FootprintImage.store()`.

**Рендер STEP.**
- OpenCascade (`cadquery-ocp`) переносит классы и методы между версиями:
  имена классов ищутся по списку модулей (`OCCT_NAMES`), статические
  методы — через `occt_call()` (`Face` или `Face_s`). Жёстких импортов из
  `OCP` не добавлять.
- Рендер никогда не идёт внутри запроса: держит GIL и замораживает сайт.
  Он отправляется через `components/tasks.py` — в воркер или отдельным
  процессом.
- На сервере без экрана виртуальный экран поднимает сам рендер
  (`ensure_display()` в `components/step.py`), обёртки вокруг команд не
  нужны.

**Миграции.**
- Переименование приложения или схемы — через SQL-скрипт в `sql/` с
  записью в `docs/schema-history.md`. Сам по себе переименованный код базу
  не трогает, а `migrate` в Docker запускается при каждом старте.
- `components/schema_guard.py` останавливает `migrate`, если таблицы Django
  лежат вне пути поиска. Если он сработал — чинить `POSTGRES_SCHEMA`, а не
  обходить проверку.

## Как вести изменения

- **Версия** — `__version__` в `config/__init__.py`, одна на проект; её
  показывает шапка сайта. Новая возможность поднимает MINOR, исправление —
  PATCH. Каждое изменение, которое увидит пользователь, записывается в
  `CHANGELOG.md` под текущей версией; то, что требует действий при
  обновлении (SQL-скрипт, новый файл, настройка в `.env`), — в раздел
  «Обновление» этой версии, с порядком шагов.

- Комментарии в коде объясняют *почему*, а не *что*: какой случай решение
  закрывает и что сломается, если его упростить. Это основной стиль
  проекта — держись его.
- Меняешь поведение — обнови документ раздела в `docs/`. Меняешь схему
  базы — `docs/schema-history.md`.
- Не удаляй чужой код ради порядка: если что-то выглядит лишним, сначала
  найди, где оно используется, и спроси.
- Сервер — рабочая система с живыми данными. Правки делаются локально и
  доставляются через git; на сервере — только `git pull` и пересборка.
  Команды, меняющие данные на сервере (`migrate`, `rm`, SQL), — только
  после явного подтверждения и при свежей резервной копии
  (`docs/deploy.md`, раздел про резервные копии).

## Превью в Claude Desktop

Сервер разработки описан в `.claude/launch.json`. Сайт закрыт логином —
включи Persist sessions в меню сервера, чтобы не входить заново после
каждого перезапуска.
